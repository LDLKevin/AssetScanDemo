# Spec：POC 盤點流程健全化（編碼 / 寫檔 / 誤觸 / 冷卻）

> 目標 issue 標題：`POC 盤點流程健全化：Big5 編碼、寫檔策略、誤觸過濾、冷卻縮短`
> 建議 label：`ready-for-agent`
> 產生日期：2026-08-20　｜　依 `/to-spec` 對真專案（`com.example.myapplication`）現況收斂

---

## Problem Statement

使用者用這支 App 做財產盤點：先在 ERP 端把財產清單匯出成 CSV，經 USB 傳到手機，現場離線掃描 QR Code 逐筆比對、寫回註記，再 USB 傳回 ERP。目前有四個會讓實地作業出錯或體感變差的問題：

1. **中文一載入就變亂碼**：ERP 匯出的 CSV 是 MS950 編碼，但 App 用系統預設編碼（Android 上是 UTF-8）讀寫，財產名稱、部門、地點全部變亂碼，盤點根本沒法用。
2. **每掃一筆就整份重寫檔案**：全盤與抽盤兩個流程每成功掃一筆就把整份（可達 3 萬筆）CSV 重寫一次，造成不必要的磁碟負擔，且萬一寫到一半程序被中止，既有檔案可能受損。
3. **相機誤觸別的 QR 會污染盤點結果**：全盤是連續掃描、相機一直開著；只要解碼成功且第一欄非空就照單全收。使用者不小心掃到現場其他 QR（別的財產、包裝上的條碼）時，會被當成「未列入清單」的盤盈，污染畫面與資料。
4. **全盤冷卻 5 秒過長**：目前全盤兩次成功掃描間要等 5 秒，拖慢連續盤點節奏。

## Solution

在不改動現有作業流程（全盤連續掃、抽盤逐筆鎖定目標）的前提下，做四項健全化：

1. **編碼改 Big5**：`CsvManager` 讀寫都明確指定 Big5、寫檔不加 BOM，讓中文正確往返 ERP。
2. **寫檔改成記憶體更新 + 定點寫檔**：掃描當下只更新記憶體中的財產清單與畫面；只有在使用者「儲存」、頁面 `onPause()`／`onStop()` 時才寫一次檔，並且先把整份內容序列化完成才動到目的檔，降低寫壞既有檔案的機會。
3. **加資產編號格式檢查**：全盤掃到的字串若不符合資產編號格式，判為誤觸，靜默忽略（不刷新畫面、不提示、不建立盤盈）；符合格式才進入「命中／盤盈」判定。
4. **全盤冷卻縮短**：因為「結果停留畫面」已由既有的 history／displayAsset 機制承載，長冷卻的原始用途已不需要，將冷卻由 5 秒縮到約 0.8–1 秒，只保留防手震連拍。

## User Stories

1. 作為財務盤點人員，我希望載入 ERP 匯出的 CSV 後中文欄位正確顯示，這樣我才看得懂在盤點哪一項財產。
2. 作為財務盤點人員，我希望盤點結果寫回的 CSV 上傳 ERP 後中文不亂碼，這樣後端才能正確接收。
3. 作為盤點人員，我希望連續掃描時不會因為每掃一筆就卡一下，這樣盤點節奏才順。
4. 作為盤點人員，我希望即使盤點到一半 App 被切到背景或被系統回收，先前掃過的結果不會整份檔案損毀，這樣我不用從頭來過。
5. 作為盤點人員，我希望相機不小心掃到現場其他 QR Code 時，畫面上正在看的財產資訊不會被莫名刷掉，這樣我能安心核對當前這一筆。
6. 作為盤點人員，我希望相機誤觸到不成格式的條碼時，系統直接忽略、不要跳出「未列入清單」，這樣盤盈清單才不會被雜訊污染。
7. 作為盤點人員，當我掃到「格式正確但清單裡沒有」的財產時，我希望系統明確提示這是盤盈（未列入清單）並讓我可以寫入，這樣真正的盤盈才不會被漏掉。
8. 作為盤點人員，當我掃到「格式正確且在清單中、但部門或地點不符」的財產時，我希望系統標記為不相符，這樣我事後能複查差異。
9. 作為盤點人員，當我掃到「格式正確、在清單中、部門地點都相符」的財產時，我希望系統標記為已盤點並記錄時間，這樣進度才會前進。
10. 作為全盤人員，我希望剛掃過的幾筆結果留在畫面上、可以用上一筆／下一筆回看，這樣掃錯或想確認時能翻回去。
11. 作為抽盤人員，我希望掃描頁只接受我當前鎖定的那一筆目標、掃到別的就提示而不誤記，這樣抽樣結果才準確。
12. 作為盤點人員，我希望縮短冷卻後仍不會因為同一張 QR 停留在鏡頭前而被連續重複記錄，這樣同一筆不會被重複盤點。
13. 作為使用單位管理者，我希望盤點結果的狀態（已盤點相符 V／不相符 X／未盤點空白）在 CSV 中維持既有欄位格式，這樣既有 ERP 匯入程式不用改。
14. 作為專案負責人，我希望資產編號格式規則之後從使用單位問到後，能只換掉一個判斷元件、不動其他邏輯，這樣格式規則變更成本最低。
15. 作為維護者，我希望掃描判定邏輯能用純單元測試涵蓋四種情況（誤觸／命中相符／命中不符／盤盈），這樣改動時能快速回歸。
16. 作為維護者，我希望 CSV 讀寫能用一個往返測試驗證中文與狀態欄位在 Big5 下正確保存，這樣編碼相關回歸能被自動抓到。
17. 作為盤點人員，我希望在光線不足處能開手電筒掃描（現有功能），且上述改動不影響它，這樣暗處作業照舊。

## Implementation Decisions

### 涵蓋模組
- `data/CsvManager`：編碼、寫檔序列化方式。
- `data/AssetRepository`：升級為記憶體資料源 + 寫檔的擁有者（新增「已變更」旗標與 `flush()`）。
- `ScanActivity`（全盤）：掃描判定改走共用判定元件；加格式檢查與誤觸靜默；冷卻值調整；改為記憶體更新 + 定點寫檔。
- `SamplingActivity`（抽盤）：改為記憶體更新 + 定點寫檔；目標比對複用共用判定元件。
- `SamplingScanActivity`（抽盤掃描頁）：可複用格式 predicate 過濾明顯雜訊（次要）。
- 新增：掃描判定純邏輯元件（見「測試接縫 A」）。

### 1. Big5 編碼
- `CsvManager.read()` 的 `InputStreamReader` 與 `write()` 的 `OutputStreamWriter` 都明確指定 `Charset.forName("Big5")`（`java.nio.charset.Charset` 已 import，目前未使用）。
- 寫檔**不得加 BOM**（Big5 家族無 BOM；加了會害 ERP 再匯入出錯）。讀取端保留現有 `BOMInputStream`（用於容錯，不主動產生 BOM）。
- CSV 欄位順序與語意維持不變：`id, name, department, location, status(V/X/空), checkedAt`。狀態對應維持 `MATCHED→"V" / UNMATCHED→"X" / UNCHECKED→""`。
- 已知邊界（不在本 spec 解決，見 Out of Scope）：Android 只有基礎 Big5、無 CP950 擴充區，MS950 專屬擴充字會顯示為 `?`／`�`。

### 2. 寫檔策略
- **掃描／寫入當下只改記憶體**（更新 `Asset` 的 `status`／`checkedAt`／新增盤盈項）與畫面，**不即時寫檔**。
- 寫檔時機收斂為：**① 使用者主動「儲存」（若無此按鈕，於掃描頁「完成」時觸發）② `onPause()` ③ `onStop()`**。
- 寫檔擁有者為 `AssetRepository`：新增「已變更（dirty）」旗標與 `flush(ContentResolver)`；`flush()` 僅在 dirty 時真正寫檔，寫完清旗標；加「寫入進行中」旗標避免重入。
- **序列化先於落檔**：先在記憶體／App 私有暫存把整份 CSV 內容完整產生，確認序列化無誤後，再對使用者選定的 SAF 文件 Uri 做單次 `openOutputStream(uri, "wt")` 寫入。這消除「序列化中途出錯留下半份檔」的風險。
- **約束說明**：使用者選檔走 SAF `OpenDocument`，拿到的是單一文件 Uri，無法用 ContentResolver 在其父目錄建暫存檔再 rename，故**無法對目的檔做真正的 rename 原子替換**。POC 接受「程序在單次寫入視窗內被中止」的殘餘小風險（此風險已由『大幅降低寫檔頻率 + onPause/onStop 自動存』縮到極小）。真正的 rename 級原子性列為上線版議題。
- 兩流程移除「每掃一次 `saveCsv()`」呼叫，改由上述時機統一 `flush()`。

### 3. 資產編號格式檢查 + 誤觸靜默
- 新增可抽換的 **id 格式判斷 predicate**（介面／函式），例如 `boolean isValidAssetId(String id)`。
- **暫定實作**：以長度／字元組成的臨時規則擋（真規則待使用單位確認，見 Out of Scope）。介面固定，之後只換實作。
- 全盤 `ScanActivity` 解碼成功後的分流（由共用判定元件輸出）：

  | 掃到的字串（取第一欄為 id） | 判定 | 處理 |
  |---|---|---|
  | id 不符格式 | 誤觸 | **靜默忽略**：不刷新畫面、不提示、不記錄 |
  | id 符格式、在清單、部門+地點相符 | 命中相符 | 標記 `MATCHED` + `checkedAt`，畫面停留 |
  | id 符格式、在清單、部門或地點不符 | 命中不符 | 標記 `UNMATCHED` + `checkedAt`，畫面停留 + 提示 |
  | id 符格式、不在清單 | 盤盈 | 顯示「未列入清單」+ 可「寫入」（維持現有行為） |

- 抽盤 `SamplingScanActivity` 目前已只接受鎖定目標 id、其餘提示；可複用同一 predicate 過濾明顯不成格式的雜訊，避免對垃圾碼跳提示（次要，可選）。

### 4. 冷卻縮短
- 全盤 `ScanActivity.COOLDOWN_MS` 由 `5000` 縮為約 `800`–`1000` ms。
- 保留「同一 raw 短時間內去重」的既有守衛（避免同一張 QR 停在鏡頭前被連續記錄），其時間窗依縮短後的冷卻對應調整。
- 「結果停留畫面」由既有 history／`displayAsset` 承載，不因冷卻縮短而失去。

### 共用判定元件（接縫 A）
- 抽出一個純邏輯元件（例如 `data` 或新 `logic` 套件下的 `ScanClassifier`），輸入：`rawString`、目前財產清單（或查找函式）、`isValidAssetId` predicate；輸出：一個結果型別涵蓋 `IGNORED_INVALID / MATCHED / UNMATCHED / SURPLUS(盤盈)`，並帶回對應的 `Asset` 或解析出的欄位。
- Activity 只負責把結果對應到 UI 與記憶體變更；判定本身不碰 Android 相機／UI，可純測。

## Testing Decisions

- **好測試的定義**：只驗證對外行為（輸入 → 輸出／狀態），不綁實作細節（不驗證私有欄位、不依賴相機或特定 UI 佈局）。

- **接縫 A：掃描判定純邏輯（JVM 單元測試）**
  - 位置比照現有 `app/src/test/.../ExampleUnitTest.java`（純 JVM）。
  - 對 `ScanClassifier` 餵各種 `raw` + 一份小型財產清單 + 一個 stub predicate，斷言輸出的結果分類與對應 asset：
    - id 不符格式 → `IGNORED_INVALID`
    - 符格式、在清單、部門地點相符 → `MATCHED`
    - 符格式、在清單、部門或地點不符 → `UNMATCHED`
    - 符格式、不在清單 → `SURPLUS`
    - 邊界：空字串、只有 id 無其他欄位、分號數量不足。

- **接縫 B：`CsvManager` 往返（Instrumented androidTest）**
  - 位置比照現有 `app/src/androidTest/.../ExampleInstrumentedTest.java`，需在裝置／模擬器上跑（Big5 是 Android 平台行為，JVM 測不準；建議至少涵蓋 minSdk API 26）。
  - 造一份含中文（部門、地點、含中文的財產名稱）與各種狀態（V/X/空）的 `List<Asset>` → `write` → `read` → 斷言與原始一致。
  - 斷言寫出的位元組**不含 BOM**。
  - 斷言以 Big5 解碼常見繁中正確；並可加一個「以 UTF-8 解讀同一位元組會不一致」的反向斷言，鎖住編碼指定沒被改回預設。

- 「何時寫檔（onPause/onStop）」與「冷卻值」屬薄膠水層，靠接縫 A/B 承載核心邏輯，本身以手動或既有 instrumented 流程驗證即可，不另立單元測試。

## Out of Scope

- **資產編號真實格式規則**：幾碼／開頭是否固定／英數位置，待與使用單位確認；本 spec 僅提供可抽換 predicate 與臨時長度規則。拿到規則後只換 predicate 實作。
- **盤盈的記錄／持久化擴充**：維持現有「提示 + 可寫入」；是否另存盤盈清單延到上線版。
- **真正 rename 級寫檔原子性**：受 SAF 單一文件 Uri 限制，POC 接受降頻 + 序列化先行後的殘餘小風險。
- **CP950 擴充字**：Android 基礎 Big5 無法呈現，個案由 ERP 匯出端先清。
- **上線版分支**：多人多機併發合併、匯出到上傳期間 ERP 異動的 re-import 衝突、盤點欄位擴充（照片／保管人）、改用 SQLite/Room。
- **查找效能索引**：3 萬筆線性比對非瓶頸，維持線性搜尋，不加 HashMap 索引。

## Further Notes

- MS950 → Big5 的裝置實測已於 API 26（本專案 minSdk）確認：`MS950`／`windows-950`／`x-windows-950` 在 Android 全部 canonical 成基礎 `Big5`，常見繁中以 Big5 解碼正確，UTF-8 則亂碼。
- 兩流程共用的 QR 解析格式為 `id;name;department;location`。
- 本 spec 執行後，`AssetRepository` 由單純的「清單 + Uri 持有者」升級為「記憶體資料源 + 寫檔擁有者」，是後續上線版把持久化換成 SQLite 時的自然接點。
- 設計脈絡與更早的決策討論見 `docs/poc-review-decisions.md`（註：該文件成文時對照的是較早的專案結構，部分「待實作」項在本專案已完成，以本 spec 的現況對照表為準）。
